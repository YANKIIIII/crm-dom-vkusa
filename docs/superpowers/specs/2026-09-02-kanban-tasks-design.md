# Канбан «Задачи»

Дата: 2026-09-02  
Статус: утверждено в обсуждении, ждёт ревью файла

## Цель

В CRM появляется личная канбан-доска в духе Trello: пункт «Задачи» в меню, страница на весь экран, три колонки. Руководитель открывает доску любого сотрудника и может на ней работать. Сотрудник видит и правит только свою.

Это не общая корпоративная доска и не вкладка на заказе или клиенте.

## Вне скоупа (не в этой версии)

- Свои колонки, переименование колонок, несколько досок у одного человека
- Описание, комментарии, чеклисты, вложения, метки, уведомления
- Календарь, фильтры, поиск по карточкам
- Общий вид «все карточки компании»

## Данные

Новое Django-приложение `tasks`. Три модели.

### Board

Одна доска на пользователя (`OneToOne` на `users.User`, `on_delete=CASCADE`).

Поля: `owner`, `created_at`, `updated_at`. Таблица `task_boards`.

### List

Колонка принадлежит доске (`ForeignKey`, `CASCADE`).

Поля:

- `board`
- `code` — slug: `todo` | `doing` | `done`
- `name` — «К работе» | «В работе» | «Готово»
- `sort_order` — 0, 1, 2
- `created_at`, `updated_at`

Уникальность: `(board, code)`. Таблица `task_lists`. Индекс по `board`.

В первой версии набор колонок фиксирован. API создания и правки колонок нет. UI «добавить колонку» нет. Модель колонки есть, чтобы не ломать форму Trello и не плодить enum на карточке.

### Card

Карточка принадлежит колонке (`ForeignKey` на `List`, `CASCADE`).

Поля:

- `list`
- `title` — обязательное, `max_length=255`, после `strip` не пустое
- `due_date` — `DateField`, необязательное
- `order` — `ForeignKey` на заказ, `SET_NULL`, необязательное
- `client` — `ForeignKey` на клиента, `SET_NULL`, необязательное
- `position` — целое ≥ 0, порядок сверху вниз внутри колонки
- `created_by` — `ForeignKey` на пользователя, `SET_NULL` (кто создал; на карточке не показываем)
- `created_at`, `updated_at`

Заказ и клиент независимы: можно оба, один или ни одного. Удаление заказа или клиента не удаляет карточку, только обнуляет ссылку.

Таблица `task_cards`. Индекс `(list, position)`.

Исполнитель не хранится отдельно: владелец доски и есть исполнитель.

### Создание доски

Функция `ensure_board(user)` идемпотентна: если доски нет — создаёт доску и три колонки с кодами `todo` / `doing` / `done`.

Вызовы:

1. `post_save` на `User` (в том числе `create_user` в тестах и админке)
2. Перед отдачей доски в API, если вдруг доски нет у старого пользователя

Миграция данных: для всех существующих `User` вызвать `ensure_board`.

Удаление пользователя каскадом уносит доску, колонки и карточки.

## Права

Новый модуль `tasks`:

- `ALL_MODULES`
- `GRANTABLE_MODULES` (можно выдать сотруднику)
- `SELLER_DEFAULT_MODULES` — вместе с `orders`, `clients`, `warehouse`

Руководитель по-прежнему получает все модули.

Миграция доступов для уже существующих сотрудников:

- Пустой `modules` не трогать: `effective_modules` возьмёт новый дефолт, в нём будет `tasks`
- Непустой список без `tasks` — дописать `tasks`
- Нельзя писать `['tasks']` в пустой список: тогда пропадут заказы/клиенты/склад

Пункт в меню берётся из `localStorage` после логина (`/users/users/me/`). После выкатки существующие сотрудники увидят «Задачи» после повторного входа. Руководитель видит пункт сразу (роль `manager`).

Матрица:

| Действие | Сотрудник с модулем | Руководитель | Без модуля |
|---|---|---|---|
| Своя доска: читать, создавать, двигать, править, удалять | да | да | API 403, нет пункта меню |
| Список чужих досок и переключатель | нет | да, только `is_active` | нет |
| Чужая доска: читать и писать | 403 | да | 403 |

Сотрудник не может подставить чужой `board` / `list` / `card` id. Руководитель может создавать карточки на чужой доске — они остаются на доске владельца.

Доска создаётся у каждого пользователя, даже без модуля `tasks`. Руководитель может открыть доску сотрудника, которому модуль ещё не выдан.

## API

Префикс: `/api/v1/tasks/`. Все эндпоинты: `IsAuthenticated` + `HasModule('tasks')`.

Колонки через API не создаются, не переименовываются, не удаляются.

### `GET /api/v1/tasks/boards/`

Список досок для переключателя.

- Сотрудник: ровно своя доска
- Руководитель: доски пользователей с `is_active=True`

Элемент: `{ id, owner: { id, username, first_name, last_name } }`.

Пагинации на этом списке нет: штат маленький, переключатель должен видеть всех активных сразу.

### `GET /api/v1/tasks/boards/<id>/`

Доска целиком. Чужой id для сотрудника — 403. Руководитель читает доску и неактивного сотрудника (в переключателе его нет, прямой id не теряется).

Ответ:

```text
{
  id, owner: { id, username, first_name, last_name },
  lists: [
    {
      id, code, name, sort_order,
      cards: [
        {
          id, title, due_date, position, list,
          order: { id, order_number } | null,
          client: { id, first_name, last_name } | null
        }
      ]
    }
  ]
}
```

Карточки в каждой колонке отсортированы по `position`, затем `id`. Колонки — по `sort_order`.

### Карточки: `/api/v1/tasks/cards/`

- `POST` — создать. Обязательны `list` и `title`. `position` по умолчанию — в конец колонки. `created_by` = текущий пользователь. Колонка должна быть на доступной доске.
- `PATCH` — название, срок, заказ, клиент, `list`, `position`. Перенос: смена `list` и/или `position`. Нельзя перенести карточку на доску другого владельца, чем та, где она лежит (даже руководителю: карточка не «переезжает» с доски Валентина на доску Алексея через drag; чтобы поставить задачу другому, руководитель открывает его доску и создаёт там).
- `DELETE` — удалить карточку.

Пересчёт `position`: в транзакции, `select_for_update` по карточкам затронутых колонок, плотная нумерация 0..n-1.

Ошибки:

- пустой `title` — 400
- колонка другой доски при переносе — 400
- нет доступа к доске — 403
- нет сущности — 404

Аудит: `write_audit` на CREATE / UPDATE / DELETE карточки, `entity_type='task_card'`.

## Экран

Маршрут `/tasks`, `RoleRoute module="tasks"`. В сайдбаре пункт «Задачи» между «Клиенты» и «Склад». `MODULE_HOME` не меняет домашнюю страницу (по-прежнему первая доступная из текущего списка, заказы остаются типичным входом сотрудника).

Страница: заголовок «Задачи», три колонки на ширину контента, фон колонок как у серых панелей CRM.

Переключатель владельца доски — только у руководителя, справа в шапке (имя + фамилия, иначе username). По умолчанию открывается доска текущего пользователя. Сотрудник переключателя не видит.

«+ Карточка» внизу колонки и клик по карточке открывают одно MUI-окно:

- название (обязательно)
- срок
- заказ — `SearchableSelect`, только если есть модуль `orders`
- клиент — `SearchableSelect`, только если есть модуль `clients`
- удаление с `confirm` из `useFeedback`

Без описания и комментариев.

На лице карточки: название; срок; номер заказа; имя клиента — что заполнено. Срок красный, если дата сегодня или раньше и колонка не `done`. Клик по чипу заказа или клиента (не по всей карточке) ведёт на `/orders/:id` или `/clients/:id`, если есть соответствующий модуль; иначе чип не ссылка.

Перетаскивание внутри колонки и между колонками. Новая зависимость: `@dnd-kit/core` и `@dnd-kit/sortable`. Оптимистичный UI: при ошибке API — тост через `useFeedback`, доска перезагружается с сервера.

Стиль — MUI 9, как остальные страницы, не копия Trello пиксель в пиксель.

## Ошибки на клиенте

- 403 на `/tasks` — как другие модули, `RoleRoute`
- Сохранение карточки — `extractApiError` в окне
- Сбой переноса — откат и тост
- Пустая доска — три колонки и «+ Карточка», без отдельного empty-state на всю страницу

## Тесты (pytest)

Обновить существующие ожидания дефолтных модулей сотрудника (сейчас `orders` / `clients` / `warehouse`) — в набор входит `tasks`. В том числе `users/test_access.py`.

Новые тесты приложения `tasks`:

1. `create_user` → одна доска и три колонки с кодами `todo`, `doing`, `done`
2. Повторный `ensure_board` не создаёт вторую доску
3. Сотрудник: `GET` своей доски 200; чужой — 403; `POST` в чужую колонку — 403
4. Руководитель: `GET` и `PATCH` карточки на доске сотрудника — 200
5. Сотрудник без модуля `tasks` — 403 на список досок
6. `PATCH` переноса меняет `list` и плотные `position` в обеих колонках
7. Пустой title — 400
8. Удаление заказа обнуляет `card.order`, карточка остаётся
9. `DELETE` карточки пишет audit `task_card`
10. Миграция/хелпер доступов: непустой `modules` без `tasks` после накатки содержит `tasks`

## Риски

- Сигнал на `User` срабатывает во всех тестах, где создают пользователя: это ожидаемо, тесты не должны полагаться на «ноль строк в tasks».
- Плотный пересчёт позиций при одновременном drag двух людей на одной доске: редкий случай в салоне; побеждает последний успешный `PATCH`, клиент перезагружает доску при ошибке.
